    XML reference¶

    XML validity¶

    A schema is available in grvl along with an example that it validates. To check the validity, use an external tool, for example xmllint.

    $ xmllint --schema <path_to_schema.xsd> <path_to_my_xml_grvl_file.xml>

    How to construct a grvl XML document?¶

    First define the root of the document.

    <doc>
    <!-- screens/special components -->
</doc>

    Then include the screens/special components in the document.

    Expressions¶

    Each attribute value and each text node can hold ${...} spans. grvl evaluates the content of a span as a JavaScript expression and puts the result in its place. The evaluation occurs one time, before any widget is built.

    <button x="${100 + 20}" width="${Math.round(screenWidth / 3)}" text="${screenWidth}x${screenHeight}"/>

    The expressions use the same Duktape context as the <script> elements, thus they can call the global functions of the GUI. grvl defines screenWidth and screenHeight before the evaluation. This makes one template sufficient for more than one display resolution.

    Write $$ for a dollar sign that is followed by a brace.

    Scripts and defines¶

    A <script> element is loaded before anything is expanded, thus a ${...} span can call the functions it declares. The same script is what the GUI uses at run time, so a helper is written once and serves both.

    A <defines> block holds plain constants. Each <define> is evaluated in document order and can use the names above it, and the block is removed from the document afterwards.

    <doc>
    <script>
        function px(value) { return Math.round(value * scale); }
    </script>

    <defines>
        <define name="scale" value="screenWidth / 1920"/>
        <define name="gutter" value="Math.round(16 * scale)"/>
    </defines>

    <customView id="home">
        <button id="ok" x="${gutter}" y="${gutter}" width="${px(240)}" height="${px(48)}"/>
    </customView>
</doc>

    The order inside the document does not matter for a function, because px() reads scale when the span calls it, which is after the defines are evaluated. It does matter for code that runs immediately: a statement at the top level of a script cannot read a <define>, because the scripts run first.

    ${...} is not expanded inside a <script> element. A script is JavaScript already, thus it reads screenWidth and the defines as plain variables.

    To keep the resolution-dependent values separate from the layout, put the <defines> block in its own file and include it:

    <doc xmlns:xi="http://www.w3.org/2001/XInclude">
    <xi:include href="metrics-1920.xml"/>
    <!-- the layout -->
</doc>

    Operators and quotation marks¶

    Write the expression in plain JavaScript. grvl escapes the XML special characters inside a span before the parse, thus >, <, && and the quotation marks are permitted with no entity:

    <label text="${screenWidth > 1280 ? "wide" : "narrow"}"/>

    An XML entity inside a span is not decoded first. Write >, not &gt;.

    Limits¶

    • The engine is Duktape, thus the language is ECMAScript 5.1. There are no arrow functions, no let and no template literals.

    • A regular expression literal in a span is not supported, because the span scanner cannot tell it from a division. Use new RegExp("...").

    • The expressions share one global object and run in document order. Thus an expression that has a side effect changes the result of the expressions below it.

    • A span in a comment, a CDATA section or a processing instruction is not expanded.

    Generic component/container attributes¶

    Each component has the following attributes:

    • id

    • x (absolute, in pixels)

    • y (absolute, in pixels)

    • width

    • height

    • visible (true/false)

    • foregroundColor

    • activeForegroundColor

    • backgroundColor

    • activeBackgroundColor

    • borderColor

    • activeBorderColor

    • borderType (one of: none, box, top, right, bottom, left)

    • borderArcRadius

    • onClick (callback)

    • onPress (callback)

    • onRelease (callback)

    Containers can also be specified as selection, which makes it a single-choice container, meaning that only one child component can be active and will remain active until another component from that container is activated.

    Generic screen attributes¶

    Each screen is a container, so it has all of the attributes from the previous section as well as:

    • onSlideToLeft (callback)

    • onSlideToRight (callback)

    • onLongPress (callback)

    • onLongPressRepeat(callback)

    • collection (string)

    • globalPanelVisible (true/false)

    It can also contain <key> that can have the following attributes:

    • id

    • onPress

    • onLongPress (callback)

    • onLongPressRepeat(callback)

    • onRelease

    Border type¶

    Attributes¶

    Derives all attributes from Button with the addition of:

    • onSwitchON - callback executed when switching to active state

    • onSwitchOFF - callback executed when switching to inactive state

    Example¶

    <SwitchButton id="test_switch" x="0" y="60" width="80" height="50" stateIndicatorArcRadius="5" stateIndicatorWidth="20" stateIndicatorHeight="20" foregroundColor="#fffcba03" backgroundColor="#ffffffff" font="roboto" onSwitchON="SwitchCallback" onSwitchOFF="SwitchCallback" />

    TextInput¶

    A single-line text field. The keyboard is shown when the field is clicked.

    Attributes¶

    • text

    • basicText (placeholder, shown while the field is empty)

    • font

    • textColor

    • activeTextColor

    • type (text or password)

    • cursor (true/false, default false)

    • cursorColor (default: the value of textColor)

    • cursorBlink (true/false, default true)

    • autoFocus (true/false, default false)

    • onTextInput

    • onSubmit

    The caret is a one-pixel line drawn after the typed text. The gap between the text and the caret, and the height the caret adds above and below the font, are both a quarter of the font height, with a minimum of one pixel. Thus an 8 pixel font gets a gap of 2 and a caret of 12, and a 26 pixel font gets a gap of 6 and a caret of 38.

    It appears only while the field has focus. A placeholder does not move it, so an empty field shows the caret at the left edge. When the text is wider than the field, the caret stops at the right edge.

    The caret blinks every 500 ms. Typing restarts the cycle, so the caret is lit while the user types. Blinking asks for a new frame on every draw, which defeats the idle throttle of SetIdleThrottle(). Set cursorBlink="false" on a device where the screen should go idle.

    Focus¶

    A text input receives the keys of Manager::ProcessTextInput() only while it is the active input. Clicking the field makes it active, and SetActiveInput does the same from JavaScript or from C++.

    A device with no touchscreen has nothing to click, so autoFocus="true" marks the field that becomes active when a screen holding it is opened. The element is found by its id at that moment, thus a field inside a prefab gives the focus to the instance on the screen and not to the prefab. Only one element can hold the request; a second autoFocus replaces the first and logs a warning. When the opening screen does not hold the element, the current focus stays as it is.

    Note that autoFocus triggers the keyboard popup, exactly as a click does, when the keyboard has autoPopup set.

    Example¶

    <TextInput id="name" basicText="Name" font="mona26"
    x="0" y="0" width="426" height="34"
    borderType="box" borderArcRadius="12"
    backgroundColor="#FF191A1C" textColor="#FF9EA2A6"
    cursor="true" cursorColor="#FFECEDEE" autoFocus="true" />

    keypadMapping¶

    SDL (LinuxDesktop) and LinuxNative install default keyboard mappings during application setup, before XML is loaded. Standard keys therefore need only an action declaration inside a view, for example:

    <key id="backspace" onPress="Backspace"/>
<key id="escape" onPress="QuitApplication"/>

    Backspace and QuitApplication here are application-provided callbacks, not built-in actions. Default IDs are identical across these backends:

    • a–z, 0–9, space, tab, enter, backspace, escape

    • minus, equals, leftbracket, rightbracket, backslash, semicolon, apostrophe, grave, comma, period, slash

    • leftshift, rightshift, leftctrl, rightctrl, leftalt, rightalt, leftmeta, rightmeta, menu, capslock

    • f1–f24, printscreen, scrolllock, pause

    • insert, delete, home, end, pageup, pagedown, left, right, up, down

    • numlock, kp_0–kp_9, kp_period, kp_divide, kp_multiply, kp_minus, kp_plus, kp_enter, kp_equals, kp_comma

    • mute, volumeup, volumedown, playpause, stop, nexttrack, previoustrack

    Letter and punctuation IDs follow SDL key symbols on desktop and physical evdev keys (US key names) on LinuxNative. Other platforms and applications that initialize Manager directly must provide their own mappings.

    keypadMapping is optional. Its entries override defaults by numeric code; unmentioned defaults remain. Giving another code the same ID adds an alias rather than removing the original binding. Codes retain their backend-specific meaning: SDL2 key symbols on desktop, evdev codes on LinuxNative. For example, Backspace is 8 on SDL and 14 on LinuxNative. Codes support unsigned 32-bit values, including full SDL special-key symbols (e.g. Left is 1073741904). Explicit legacy bindings using truncated 16-bit SDL codes are still honored ahead of backend defaults; an explicit full-width binding takes precedence over a legacy binding. New XML should use full-width values to avoid the ambiguity of truncated codes.

    LinuxNative retains its existing modifier encoding: OR the evdev code with 1024 for Ctrl, 2048 for Alt, and 4096 for Shift. Exact modified mappings take precedence, falling back to the unmodified code. SDL continues to send key symbols without this modifier encoding.

    Contains key elements with the following attributes:

    • id

    • code (int)

    • repeat (int, optional; repeat interval in milliseconds, default 100)

    Example¶

    <keypadMapping>
    <key id="space" code="456" repeat="200"/>
    <key id="enter" code="789" repeat="100"/>
</keypadMapping>
